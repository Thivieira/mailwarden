# systemd units

```text
proton-bridge.service      # official Proton Mail Bridge — Proton owns this lifecycle
mailwarden-bridge.service  # Mailwarden Bridge daemon: gateway + tunnel + heartbeat
mailwarden-gateway.service # legacy: gateway only, pre-device-identity relays
```

`mailwarden-bridge.service` is generated by `planSystemdInstall()` in
`apps/bridge/src/core/service.ts`, so the checked-in file, `mailwarden-bridge service
install`, and the AlmaLinux installer cannot drift apart. Regenerate it rather than
hand-editing:

```bash
bun -e 'import {planSystemdInstall} from "./apps/bridge/src/core/service";
  await Bun.write("infra/systemd/mailwarden-bridge.service",
    planSystemdInstall({execPath:"/usr/local/bin/bun",
      daemonPath:"/opt/mailwarden/apps/bridge/src/daemon.ts"}).unitContents)'
```

The Bridge unit runs unprivileged (`User=mailwarden`), with `NoNewPrivileges`,
`ProtectSystem=strict`, `ProtectHome`, `UMask=0077`, and write access only to its state
directory. It is ordered after Proton Bridge but does not `Requires=` it: Bridge reports
Proton as unhealthy instead of refusing to start, so a broken relay stays diagnosable.

`cloudflared` needs no unit here. The Bridge daemon starts it with the device's scoped
tunnel credential, and if a host already runs its own `cloudflared` service, Bridge
detects the active unit and leaves it alone.

Never put `PROTON_GATEWAY_API_KEY`, Bridge-generated passwords, device credentials, or
tunnel tokens in a unit file or in Git. The Bridge unit carries no secrets at all;
credentials live in the Bridge secret store under the state directory.

Install with `infra/almalinux/install-bridge.sh`, or read
[`docs/operations/ALMALINUX.md`](../../docs/operations/ALMALINUX.md).
